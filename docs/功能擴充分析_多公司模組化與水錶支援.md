# SLGAS 功能擴充分析報告：多公司模組化與水錶支援

本報告由 **樂鑫 ESP SDK Matter 高級顧問與 Apple HomeKit 資深工程師** 針對 SLGAS 整合的擴充需求進行深度分析。

---

## 1. 需求分析

目前 SLGAS 整合已具備「拍照 -> AI OCR 辨識 -> 網站上報」的完整流程，但主要邏輯硬編碼（Hardcoded）於欣隆天然瓦斯（SLGAS）。
用戶提出以下兩大擴充方向：
1. **多瓦斯公司支援**：允許使用者選擇不同的天然瓦斯公司，並使用對應的模組進行上報。
2. **跨類別支援（水錶）**：在同一架構下新增「水錶」類別，支援水錶拍照、辨識與上報。

---

## 2. 現有架構評估

根據 `report_service.py` 與 `config_flow.py` 的代碼分析：
- **OCR 邏輯**：目前使用 Google AI，具備高度通用性，僅需調整 `prompt` 即可支援水錶。
- **上報邏輯**：`_submit_to_slgas` 方法與欣隆瓦斯官網高度耦合（含特定欄位如 `CusNo`, `ChkField` 及 Big5 編碼），不利於直接擴充。
- **設定流**：目前為單一瓦斯公司的欄位設計。

---

## 3. 模組化設計方案

### 3.1 抽象化上報層 (Reporter Provider)
建議導入 **Provider 模式 (Provider Pattern)**，將不同公司的上報邏輯抽離。

1. **建立 Provider 基底類別**：
   定義統一的接口（如 `async def submit(self, degree: str) -> bool`），規範所有模組必須實作的方法。
2. **建立模組目錄**：
   新增 `custom_components/slgas/reporters/` 目錄，存放各家公司的實作模組：
   - `slgas.py` (欣隆)
   - `taipeigas.py` (大台北瓦斯)
   - `water_taipei.py` (台北自來水)
3. **工廠模式動態加載**：
   `SlgasReportService` 根據設定中的 `company_id` 動態實例化對應的 Provider。

### 3.2 設定流 (Config Flow) 調整
為了提供良好的使用者體驗，建議修改設定流程：

- **第一步 (Type Selection)**：選擇類別（瓦斯 / 水錶）。
- **第二步 (Company Selection)**：根據類別過濾顯示支援的公司清單。
- **第三步 (Dynamic Fields)**：根據所選公司顯示特定的必填欄位（例如有些公司需要電號、有些需要水號）。

---

## 4. 水錶支援實施細節

### 4.1 感測器 Metadata 差異化
水錶與瓦斯錶在 Home Assistant 中屬於不同的 `device_class`：
- **瓦斯**：`device_class: gas`, `unit_of_measurement: m³`。
- **水**：`device_class: water`, `unit_of_measurement: m³` 或 `L`。

**解決方案**：在 `sensor.py` 中，根據用戶選擇的類別動態設定感測器的屬性，確保能正確顯示於 HA 的能源 (Energy) 面板。

### 4.2 OCR Prompt 模板化
水錶的刻度讀取邏輯可能與瓦斯錶略有不同（例如某些水錶有小數點或多個紅色指針）。
- 建立 `PROMPT_TEMPLATES`，針對不同的錶類提供優化的 AI 指令。
- 預設水錶 Prompt 範例：「這是一張水錶的照片，請提取黑色數字部分的整數度數，忽略紅色小數部分...」。

## 5. 架構演進建議 (資深工程師觀點)

作為資深 IoT 工程師，我建議在擴充時考慮以下優化：

### 5.1 整合命名建議
由於功能已擴展至水錶與多家公司，建議考慮將 `slgas` 域名 (Domain) 保持不變以相容現有用戶，但顯示名稱改為 **"通用能源自動報表 (Universal Utility Reporter)"**。

### 5.2 錯誤處理與日誌
各家網站的 HTML 結構差異極大，模組化後應強化 **自定義異常處理**。當某家公司改版導致爬蟲失效時，能精確回報是「欣隆瓦斯模組失效」而非「整個整合壞掉」。

### 5.3 HomeKit 與 Matter 潛力
雖然目前主要是網站上報，但作為 HomeKit 專家，我建議將辨識出的度數同步暴露為 HomeAssistant 的感測器。透過 HA 的 HomeKit Bridge，使用者可以直接在 Apple Home App 中查看目前的瓦斯/水錶讀數（雖然 HomeKit 對 Gas 的原生支援有限，但可透過自定義感測器實現）。

## 6. 多條目支援 (Multi-Instance Support) 評估

針對您詢問「是否能支援新增多條不同的水和瓦斯條目」，這是 Home Assistant `ConfigEntry` 架構的核心優勢：

### 6.1 實作原理
Home Assistant 允許同一個整合（Domain: `slgas`）被使用者安裝多次「條目 (Entries)」。
- 系統會為每一個條目生成一個唯一的 `entry_id`。
- 所有的數據（度數、歷史紀錄、狀態）都會根據 `entry_id` 進行隔離。
- 這樣設計後，使用者可以在整合頁面點擊「新增條目」，分別建立：
    1. 「家裡的瓦斯」
    2. 「租屋處的瓦斯」
    3. 「頂樓的水錶」

### 6.2 資源隔離與併發
- **獨立排程**：每個條目可以設定不同的 `schedule_time`（例如瓦斯早上報，水錶晚上報）。
- **獨立實體**：每個條目會產生自己的一組感測器實體（例如 `sensor.gas_meter_12345` 與 `sensor.water_meter_67890`）。
- **共用辨識核心**：雖然有多個條目，但它們共用同一個 Google AI 辨識邏輯，節省資源。

### 6.3 對用戶的效益
這種架構非常適合擁有多個水電瓦斯錶的用戶（如民宿業者、多房產用戶）。所有的管理都在同一個 UI 下完成，不需要安裝多個不同的 HACS 整合。

## 7. HACS 架構相容性分析

針對您詢問「HACS 這樣的架構是否做得到」，答案是：**絕對可以，且這正是 Home Assistant/HACS 標準的推薦做法。**

### 6.1 HACS 只是傳輸載體
HACS 本質上是將您的 `custom_components/slgas/` 整個資料夾下載到使用者的系統中。只要資料夾內的結構符合 Home Assistant 的標準，HACS 就能完美支援。

### 6.2 模組化目錄結構 (符合 HACS 規範)
我們可以將結構設計如下，這在大型 HACS 整合中非常常見：
```text
custom_components/slgas/
├── reporters/            <-- 新增模組目錄
│   ├── __init__.py
│   ├── base.py           # 定義標準接口
│   ├── slgas.py          # 欣隆模組
│   └── water_taipei.py   # 台北自來水模組
├── config_flow.py        # 處理多步驟 UI 選擇
├── sensor.py             # 根據選擇動態建立 Gas 或 Water 實體
└── manifest.json         # 定義依賴 (如 beautifulsoup4)
```

### 6.3 靈活的 Config Entry
Home Assistant 的 `ConfigEntry` 允許同一個整合被安裝多次（例如：一次裝瓦斯報表、一次裝水錶報表）。
- 每一個「實體 (Instance)」可以有獨立的設定。
- 這樣使用者就能在 HACS 中只裝一個 `slgas` 整合，但在 HA 介面新增兩個「條目 (Entries)」：一個選瓦斯、一個選水錶。

### 6.4 動態翻譯與 UI
透過 `strings.json` 的 `step` 分層，HACS 整合能提供非常專業的引導式介面。這讓「選公司 -> 填資料」的流程看起來就像官方整合一樣專業。

---

## 7. 結論與後續行動

這套架構是完全可行的。透過 **「類型選單 -> 公司模組 -> 動態欄位」** 的層次，您可以輕鬆地在不改動核心辨識邏輯的情況下，無限擴充新的服務提供商。

**後續建議行動 (待您確認後執行)**：
1. 建立 `reporters/` 目錄架構。
2. 重構 `report_service.py` 將欣隆邏輯轉移至獨立模組。
3. 擴充 `translations` 以支援類別選擇的介面顯示。
